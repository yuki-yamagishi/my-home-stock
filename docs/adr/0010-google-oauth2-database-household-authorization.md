# [ADR-0010] Google OAuth2認証とデータベース駆動型世帯・メンバー管理（パターンB）の導入

* **ステータス**: 承認済
* **日付**: 2026-09-14
* **決定者**: プロジェクトオーナー, 開発チーム

---

## 1. 文脈と問題提起 (Context)

ADR-0007 による OCI Single JAR アーキテクチャおよび Caddy リバースプロキシによる常時 HTTPS（`https://ymgs-mhs-j.duckdns.org`）の開通に伴い、アプリケーションがパブリックインターネット上に本番稼働した。
しかし、これまでの機能先行開発により、以下の重大なセキュリティおよびデータ分離上の課題が顕在化した：

1. **認証認可の欠落による不正アクセス・改ざんリスク**:
   - Spring Security で全エンドポイントが `permitAll()` のまま公開されており、URL を知る第三者やボットが自由に在庫データを閲覧・追加・改ざん・削除できる状態にあった。
2. **クライアント主導の世帯分離の脆弱性**:
   - リクエストヘッダー `X-Household-Id` をクライアントが任意に指定できる設計となっており、ヘッダーの書き換えによって他人の世帯データへ容易になりすましアクセスできる脆弱性があった。
3. **場当たり的なパッチワーク（パターンA）の排除**:
   - 「環境変数のカンマ区切りホワイトリスト」で一時しのぎを行った場合、将来的な家族招待やユーザー管理への移行時にスキーマ・認可ロジック・UI の全レイヤーに及ぶ全面破壊的リファクタリング（技術的負債）が発生する。

---

## 2. 決定内容 (Decision)

大局的視点に基づき、コアドメインである「世帯」と「ユーザー」を最初から正攻法で設計する **「パターン B（Google OAuth2 + DB 世帯・メンバーモデル）」** を正式採用する：

1. **インフラ境界防御（常時 HTTPS & 生ポート隠蔽）**:
   - OCI 外部には Caddy リバースプロキシのポート 443（HTTPS）および 80（HTTPSリダイレクト）のみを開放。
   - Spring Boot の生ポート 8080 および PostgreSQL の 5432 は外部公開を完全撤廃し、Docker 内部ネットワークに隠蔽。
2. **Google OAuth2 / OIDC パスワードレス認証**:
   - `spring-boot-starter-oauth2-client` を導入し、家族が日常的に利用する Google アカウントによる 1 タップ認証を採用。パスワード管理負荷と漏洩リスクを根絶。
   - Client ID および Client Secret は Git に一切コミットせず、OCI サーバーの `.env`（Git管理外）から環境変数経由で安全に注入。
3. **データベース駆動型の世帯マルチテナント基盤（Flyway V2）**:
   - `users` テーブル: Google の一意ユーザー識別子（`google_sub`）、メールアドレス、表示名、アイコンを永続化。
   - `households` テーブル: 世帯単位のエンティティ（ID, 世帯名, 作成者）。
   - `household_members` テーブル: 世帯とユーザーの多対多リレーションおよびロール（`OWNER`, `MEMBER`）。
   - 初回ログイン時に自動でユーザーと初期世帯を作成・紐付けるセルフブートストラップ機構を配備。
4. **サーバー主導の世帯認可境界（クライアント偽装の根絶）**:
   - `StockItemController` において、クライアントが送信する `X-Household-Id` ヘッダーを廃止。
   - Spring Security の認証プリンシパルからサーバー側で所属世帯を一意に特定し、サービス層へ渡すアーキテクチャを強制。
   - 未認証リクエストは `401 Unauthorized` で遮断。世帯に属していないユーザーは他人の在庫に一切アクセスできない認可境界を確立。
5. **段階的 UI ロードマップ**:
   - MVP: Google ログイン画面、ヘッダーへのユーザー・世帯表示、家族の Google メールアドレスを登録するシンプルな家族追加モーダル。
   - 発展: 招待リンク発行、QRコード参加機能の無破壊追加。
6. **完全プライベートアクセスガード（未認可ユーザーの門前払いと OCI 容量食いつぶし防止）**:
   - パブリック公開環境において、第三者やボットによる勝手な世帯作成・データ登録によって OCI（Always Free DB）の容量が食いつぶされるリスクを物理的に排除。
   - 認可対象を「環境変数 `ALLOWED_EMAILS` に指定されたオーナー」または「既存世帯オーナーから事前招待されたメールアドレス（`household_members.invited_email`）」に厳格限定。
   - 未認可アカウントのログイン試行時は、DB レコード（`users`, `households`, `household_members`）を 1 行も作成する前に `UserHouseholdSyncService` の冒頭で即座に `OAuth2AuthenticationException`（`access_denied`）を送出し、DB 容量消費ゼロで完全にアクセスを拒絶。
   - 拒絶されたアカウントにはログイン画面上で「このアプリは許可された家族専用です。アクセス権限がありません。」と明確にフィードバック。

## 3. 結果・影響 (Consequences)

### メリット (Positive)
- **物理的セキュリティの確立**: 未認証アクセスが 100% 遮断され、パブリック公開環境でも安全に運用可能。
- **優れたモバイル / PWA UX**: パスワード不要で、スマホ（PWA）から 1 タップでセキュアにログイン可能。
- **無破壊な拡張性**: コアドメインが最初から DB リレーションとして存在するため、将来のロール管理や複数世帯対応で手戻りが発生しない。
- **シークレット漏洩ゼロ**: 公開リポジトリに機密情報が混入しない安全な CI/CD・運用構成。

### デメリット・トレードオフ (Negative / Trade-offs)
- **Google Cloud Console での事前登録**: 運用環境ごとに OAuth クライアント ID / Secret の発行およびリダイレクト URI の登録が必要。
- **初期実装スコープの増加**: パターン A（環境変数のみ）に比べて、DB テーブル新設、認証サービス、ログイン UI の実装ボリュームが増加する（ただし大局的な手戻り防止により相殺）。

---

## 4. 代替案 (Alternatives Considered)

- **Basic 認証によるインフラ層の一時保護**:
  PWA やモバイルのセッション管理と相性が悪く、アプリケーション側の認可脆弱性を放置したパッチワーク（つぎはぎ改修）であるため却下（憲章第1.3条違反）。
- **環境変数ホワイトリスト（パターン A）**:
  短期的には実装が容易だが、家族招待やマルチテナント化への移行時に全層の破壊的リファクタリングを招くため却下。
