# [ADR-0012] 測量不要な消耗品向け「4段階残量レベル管理」と個数管理のハイブリッドデータモデル

* **ステータス**: 承認済
* **日付**: 2026-09-16
* **決定者**: プロジェクトオーナー, 開発チーム
* **関連 ADR**: ADR-0001, ADR-0003, ADR-0004

---

## 1. 文脈と問題提起 (Context)

家庭内で管理される在庫アイテムには、以下の 2 系統が混在している：
1. **個数管理品**: 牛乳（2本）、缶詰（5個）、納豆（3パック）など、個数を正確に数えて管理するもの。
2. **測量困難な単一常備品（消耗品）**: 調味料（塩、砂糖、マヨネーズ）、洗剤、シャンプー、ボディーソープ、米など、常に1袋・1ボトルのみ常備され、開封して消費されるもの。

後者に対してグラム数やミリリットル数を都度測量・入力することは非現実的であり、現在のシステムのように個数「1」または「0」だけで管理すると、「まだ1あると思っていたら料理の途中で切れた」「もう無いと思って買ったら半分以上残っていた」という買い忘れ・過剰購入が発生する。

これらを直感的に管理するため、4段階の残量ステータス（十分、まだまだ、怪しい、すっからかん）で表現できる仕組みが必要となった。

---

## 2. 決定内容 (Decision)

以下のアーキテクチャ方針に基づき、**「個数管理（`QUANTITY`）と残量段階管理（`REMAINING_LEVEL`）のハイブリッドデータモデル」** を採用する：

1. **在庫管理タイプ（`StockType`）の導入**:
   - `QUANTITY`: 従来の個数カウント管理。数量 `quantity` (Integer), 単位 `unit`, 最小閾値 `minThreshold`。
   - `REMAINING_LEVEL`: 4段階の残量レベル管理。残量レベル `remainingLevel` (Enum), 単位 `unit`。
   - 既存レコードはデフォルト `QUANTITY` とし、後方互換性を 100% 維持。
2. **4段階残量レベル（`RemainingLevel`）の定義**:
   - `FULL`: 「十分」（たっぷりある・新品〜7割以上）
   - `PLENTY`: 「まだまだ」（余裕あり・半分程度）
   - `LOW`: 「怪しい」（残りわずか・そろそろ買い足したい）
   - `EMPTY`: 「すっからかん」（なし・底をついた）
3. **二重防壁（内部数量との同期による多重整合性）**:
   - `REMAINING_LEVEL` の場合でも、内部的に `quantity` を `EMPTY=0`, `LOW=1`, `PLENTY=2`, `FULL=3` と同期させ、`minThreshold=1` を保持。
   - これにより、仮に古いクエリや外部連携が走った場合でも `LOW` や `EMPTY` が安全に不足品として抽出される。
4. **買い物リストとの自動連携**:
   - 残量管理アイテムにおいて、`remainingLevel` が `LOW`（怪しい）または `EMPTY`（すっからかん）になった場合に自動で買い物リストに追加。
   - 買い物リストには「補充完了 (十分にする)」ボタンを提供し、ワンタップで `FULL` へ復帰させてリストから解消。
5. **一覧カードでのワンタップステータス更新**:
   - カード上に 4 つの残量ボタングループを配置し、詳細モーダルを開くことなくワンタップで残量を即時更新可能とする。
   - 楽観排他制御バージョン（`version`）を必ず伝播し、複数端末での競合（409 Conflict）を検知。

---

## 3. 結果・影響 (Consequences)

### メリット (Positive)
- **家庭内の実態に即した UX**: 調味料や洗剤などの残量を測量の手間なくワンタップで記録可能。
- **買い忘れ・二重買いの防止**: 「怪しい」段階で自動的に買い物リストに入るため、使い切る前に補充できる。
- **完全な後方互換性**: 既存の個数管理アイテムや API 契約を一切破壊しない。
- **型安全性 100%**: OpenAPI 3.0 仕様書と TypeScript 型定義を完全同期。

### 留意点 (Negative / Trade-offs)
- 新規登録・編集 UI に管理種別の切り替えが必要となり、UI コンポーネントの状態管理が若干増加する（純粋ドメイン関数への分離で複雑性を封じ込める）。
