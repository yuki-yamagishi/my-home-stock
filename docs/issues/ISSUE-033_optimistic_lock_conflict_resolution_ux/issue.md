# [ISSUE-033] 楽観排他制御（409 Conflict）発生時の入力データ保護と競合解決UIの実装

* **ステータス**: 🔵 `status: in-progress`
* **種別**: 🟢 `type: feature` / 🎨 `type: ui/ux` / 🛡️ `type: stability`
* **担当者**: AIエージェント
* **作成日**: 2026-10-05
* **関連 GitHub Issue / PR**: [GitHub Issue #33](https://github.com/yuki-yamagishi/my-home-stock/issues/33) / ADR-0003

---

## 1. 解決すべき課題・背景 (Why)

1. **他端末競合時における入力データの理不尽な強制破棄（Data Loss）の解消**:
   - バックエンドでは JPA `@Version` による楽観的排他制御（ADR-0003）および HTTP 409 Conflict が堅牢に設計されている。
   - しかしフロントエンドの既存実装（`frontend/src/App.tsx` の `onError`）では、409 Conflict 検知時に `setEditingItem(null)` を呼び出して編集モーダルを強制的に閉じてしまう。
   - モーダルがアンマウントされることで、ユーザーが時間をかけて入力・推敲した品名、賞味期限、詳細な保管場所メモなどのフォーム値（`EditStockModal` 内のローカル state）が跡形もなく破棄・消滅する。
   - 家族で共有する家庭内在庫管理において、一方が編集している最中にもう一方が数量を「購入完了 (+1)」や「消費 (-1)」することは日常茶飯事であり、そのたびに入力データが蒸発する挙動は致命的な UX 破壊である。

2. **ブロッキングダイアログ `alert()` の完全排除**:
   - `frontend/src/hooks/useStockItems.ts` の `useUpdateStock` フックでは、409 エラー時にブラウザ標準の同期的な `alert()` を直接呼び出している。
   - モバイル PWA 環境において、画面全体をブロックする `alert()` は操作性を著しく損ない、エラーの文脈や解決手段も伝わらない。

3. **競合解決（Conflict Resolution）の提供**:
   - 409 Conflict は「排他制御が正常に機能し、データの先祖返りを防いだ」ことを意味する正常系のエッジケースである。
   - しかし現在のシステムは競合を通知してデータを捨てるだけで、「他端末で何が変更されたのか」を確認する手段も、「自分の入力内容で上書き保存する（最新バージョンとして送信）」か「最新データを取り込む」かを選択する手段も一切提供していない。
   - 最新データを取得して差分を明示し、ユーザーの明確な意思決定によって競合を解消できる UI/UX が不可欠である。

---

## 2. 排除するリスク (Risks to Eliminate)

1. **入力データの蒸発・消失リスク（Data Loss Risk）の排除**:
   - 409 Conflict が発生してもモーダルを閉じず、フォームの入力値（ローカル state）を確実に保持する。
2. **無限競合ループ・再送信拒絶リスクの排除**:
   - 過去の ISSUE-008 でモーダル強制クローズが導入された原因は「古い version を保持したまま再送信すると永久に 409 になる」ことであった。最新のサーバーデータを再取得して最新の `version` をフォームに安全に引き継ぎ、古い version による無限ループを物理的に排除する。
3. **同期 UI ブロッキングリスクの排除**:
   - ブラウザ標準 `alert()` を完全に撤廃し、モーダル内の視覚的なインライン警告バナーに移行する。
4. **無自覚なデータ先祖返りリスクの排除**:
   - 他端末で更新された最新の値（例: 残量が「空」になった、数量が変更された等）をインラインで提示し、ユーザーが「最新データを取り込む」か「自分の入力で上書きする」かを明示的に選択させることで、他者の更新を意図せず潰してしまうリスクを排除する。

## 3. 受け入れ基準 (Acceptance Criteria / DoD)

- [ ] `useUpdateStock` フックから `alert()` が完全に撤廃され、409 エラーが呼び出し元に安全に伝播すること。
- [ ] 編集モーダル（`EditStockModal`）で更新を送信し、サーバーから 409 Conflict が返却された場合、モーダルが閉じられずに開いたまま維持され、入力中のフォーム値（品名、カテゴリ、管理方法、数量/残量、単位、閾値、賞味期限、メモ）が一切破棄されないこと。
- [ ] 409 Conflict 発生時、編集モーダル内にインライン警告バナー（「⚠️ 他の端末によって内容が更新されました」）が表示されること。
- [ ] 競合警告バナー内またはモーダル内に、他端末で更新された最新のサーバーデータ（最新数量/残量、期限、メモ等）が確認可能であること。
- [ ] 競合発生時に以下の 2 つの競合解決アクションが選択可能であること：
  - **「自分の入力で上書き保存」**: サーバーの最新 `version` を適用して現在の入力内容で再送信し、正常に更新完了すること。
  - **「最新データを取り込む」**: サーバーの最新データで入力フォームを更新し、競合警告をクリアして再編集可能にすること。
- [ ] 競合解決後に更新が成功した場合、モーダルが正常に閉じられ、在庫一覧が最新化されること。
- [ ] 単体テスト（`frontend/tests/components/EditStockModal.test.ts` 等）が追加され、409 発生時の入力値保持、インライン警告表示、最新データ取り込み、最新バージョンでの上書き送信が検証され PASS すること。
- [ ] `npm.cmd run check`（シークレット、ドキュメント整合性、型検査、テスト全件、プロダクションビルド）が 100% 合格すること。

## 4. 機能受け入れシナリオ (Given-When-Then & 境界値・異常系)

### シナリオ 1: 409 Conflict 発生時の入力保持と警告表示（異常系）
- **Given**: ユーザー A がアイテム「牛乳」（version: 1）の編集モーダルを開き、賞味期限を「2026-10-10」、メモを「低脂肪乳を購入すること」と入力した。
- **When**: ユーザー A が「更新する」を押す直前に、別端末の家族 B が数量を消費してサーバーの version が 2 に更新され、ユーザー A のリクエストに 409 Conflict が返却された。
- **Then**:
  - `alert()` は表示されない。
  - 編集モーダルは閉じずに開いたままである。
  - ユーザー A が入力した「2026-10-10」および「低脂肪乳を購入すること」は入力欄にそのまま保持されている。
  - モーダル上部に「⚠️ 他の端末によって内容が更新されました」というインライン警告バナーが表示される。

### シナリオ 2: 競合解決「自分の入力で上書き保存」（正常系）
- **Given**: シナリオ 1 の競合警告が表示された状態である。
- **When**: ユーザー A が「自分の入力で上書き保存」ボタンを押す。
- **Then**:
  - 最新の version (2) が適用され、ユーザー A の入力値（期限: 2026-10-10, メモ: 低脂肪乳...）がサーバーに送信される。
  - サーバーで正常に更新（HTTP 200）され、モーダルが閉じられる。
  - 一覧画面にユーザー A の更新内容が反映される。

### シナリオ 3: 競合解決「最新データを取り込む」（正常系）
- **Given**: シナリオ 1 の競合警告が表示された状態である。
- **When**: ユーザー A が「最新データを取り込む」ボタンを押す。
- **Then**:
  - 家族 B が更新した最新データ（最新数量、最新 version）がフォームの入力欄に反映される。
  - 競合警告バナーが解除され、通常編集モードに復帰する。
